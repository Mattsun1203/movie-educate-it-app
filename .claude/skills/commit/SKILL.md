# コミット作成フロー

Gitコミットを作成するときは、必ずこの手順に従う。**ユーザーの承認を得るまで `git commit` を実行してはいけない。**

## 手順

1. 以下を並行して確認する。
   - `git status` （未追跡ファイルを含む変更全体の把握。`-uall` は使わない）
   - `git diff` / `git diff --staged` （変更内容の把握）
   - `git log --oneline -10` （このリポジトリのコミットメッセージの書き方・スタイルを踏襲するため）
2. 変更内容を分析し、コミットに含めるべきファイルを判断する。
   - `.env` や認証情報など、秘密情報を含む可能性のあるファイルは含めない。含めるべきか怪しい場合はユーザーに確認する。
   - `git add -A` や `git add .` のような無差別なステージは避け、対象ファイルを明示的に指定する。
3. コミットメッセージ案を作成する。
   - **本文は必ず日本語で書く。** prefix部分（`feat`等の英単語）を除き、要約文は日本語にする。
   - 「何を変えたか」より「なぜ変えたか」を簡潔に（1〜2文程度）まとめる。
   - **メッセージの先頭には必ず以下のいずれかの prefix を `<prefix>: <メッセージ>` の形式で付与する。**
     - `feat`: 新機能の追加
     - `fix`: バグ修正
     - `refactor`: 振る舞いを変えない内部構造の改善
     - `docs`: ドキュメントのみの変更
     - `chore`: ビルド設定・依存関係更新など機能に関わらない雑務
     - `test`: テストコードの追加・修正のみ
     - `style`: 動作に影響しないフォーマット・空白・セミコロンなどの変更
   - 変更内容がどの prefix にも明確に当てはまらない場合は、最も近いものを選び、判断に迷った場合はユーザーに確認する。
4. **コミットを実行する前に、ステージ予定のファイル一覧とコミットメッセージ案をユーザーに提示し、明示的な承認を求める。**
   - 承認が得られるまで `git commit` を実行しない。
   - ユーザーから修正指示があれば、メッセージやステージ対象を修正して再度提示する。
5. 承認を得たら、対象ファイルをステージし、承認されたメッセージでコミットを作成する。
   - コミットメッセージの末尾には以下を付与する:
     ```
     Co-Authored-By: Claude Sonnet 5 <noreply@anthropic.com>
     ```
   - メッセージは必ずHEREDOCで渡す。
6. コミット後、`git log --oneline -1` などで結果を確認し、ユーザーに完了を報告する。

## 注意事項

- ユーザーから明示的に依頼されていない限りコミットを作成しない。
- `--amend` は明示的に依頼された場合を除き使わない。amendする場合、直前のコミットが未pushであることを確認する。
- pre-commitフックが失敗した場合は原因を修正し、新しいコミットとして作り直す（`--no-verify` は使わない）。
- リモートへの `push` はこのスキルの範囲外。別途明示的な依頼があるまで行わない。
